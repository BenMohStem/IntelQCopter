# ESP32 FC with only MPU6050 and BMP280

The original [flight_controller.cpp](../firmware/src/flight_controller.cpp) is the implementation to use. No temporary main.cpp is needed. It uses Arduino Wire, the Electronic Cats MPU6050 library, Adafruit BMP280, Xbox BLE and Preferences. Required sensor hardware is **MPU6050 + BMP280 only**. No lidar, HMC5883L or ROS2 computer is needed for stable Xbox mode. This is a bench firmware build: motor pins stay INPUT_PULLDOWN; no ESC pulses or physical arming.

## Connect the sensors

| ESP32-S3 carrier | MPU6050 | BMP280 |
|---|---|---|
| GND | GND | GND |
| Verified regulated 3.3V sensor rail | Compatible module VCC | Compatible module VCC |
| GPIO9 / SDA | SDA | SDA / SDI |
| GPIO8 / SCL | SCL | SCL / SCK |

Both devices share Wire at 400kHz. Use 3.3V-compatible modules and pull-ups; never pull ESP32 I2C to5V. The exact breakout pin order and regulator must be checked, so map by signal rather than physical pin position. On an SPI/I2C BMP280 breakout, CSB/CS must be high for I2C; SDO selects its address as specified by that module. The MPU INT pin is not needed: the firmware polls its data-ready register. MPU AD0 selects0x68 or0x69; firmware detects either. BMP280 uses0x76 or0x77; firmware detects either. A BME280, BMP180 or MPU6500 is not interchangeable with these drivers.

On the carrier, J4 is MPU6050 and J5 is BMP280, both GND /3V3 /SDA /SCL. J6 magnetometer and J13 lidar may remain empty. Insulated links W1, W12 and W15 carry the sensor supply/SCL/SDA and must still be installed; fit other carrier links needed by the chosen interfaces. W21 must be removed before USB powering the DevKit. No ROS computer supply runs through this board.

## What runs and what remains unavailable

- Roll/pitch: accelerometer + gyro filtering, angle outer loops and angular-rate inner loops.
- Yaw: gyro-rate control. No magnetometer is read or required; compass heading is unavailable and integrated yaw drifts.
- Height: pressure relative to boot ground reference plus gravity-corrected vertical acceleration; vertical-speed commands from the centred throttle stick.
- No lidar height correction. Barometric drift, prop wash and accelerometer bias affect altitude.
- No onboard XY position/velocity measurement. Returning roll/pitch sticks to centre levels the aircraft; it cannot guarantee horizontal braking or position hold with these two sensors. The simulation's ideal horizontal localization is not available on this hardware.
- ROS2 remains optional in the normal build. Real autonomous navigation would additionally need validated localization/perception and interfaces; plugging in a computer alone does not provide those measurements.
- Missing or stale MPU6050/BMP280 data remains a sensor fault. Missing lidar/magnetometer does not cause a fault. No dummy sensor data is generated on hardware.
- Battery voltage/current hardware drivers are still unfinished. This two-sensor setup does not measure battery state of charge or provide a physical battery cutoff.

## Build

From the ESP32 project root:

```powershell
.\qcopter.ps1 build
```

That keeps optional companion UART support. To compile out ROS2 UART completely:

```powershell
.\qcopter.ps1 build-standalone
```

The application remains one .cpp plus the declaration header and the existing PlatformIO library configuration. Keep the canonical filename; do not add another .cpp defining setup/loop beside it. If moving to another project, copy the source, fc_api.h, library/version settings and Xbox patch script together. The curated reading copy is [here](../important_sources/firmware/esp32/flight_controller.cpp); build from the project root.

## Startup and calibration

Open the serial monitor at115200baud. A new SENSORS line reports the actual detected I2C addresses and explicitly prints lidar=NOT_REQUIRED and magnetometer=NOT_REQUIRED. Addresses of missing devices are0x00. **This describes expected output, not a captured real-board log.** If a required sensor is missing or configuration readback fails, fix the device/wiring and reboot; automatic hot-plug recovery is not implemented.

1. Keep the board still after boot. Gyro verification needs500 accepted stationary samples; barometer baseline needs100 accepted pressure samples. These run concurrently. Motion/noise can restart calibration, so elapsed wall time varies.
2. Stored IMU calibration is loaded from NVS when the record matches the board/profile/CRC. Gyro bias is rechecked at every boot; the pressure baseline is rebuilt each boot.
3. On first use, capture all six accelerometer orientations. Put the sensor still with the specified axis measuring approximately+1g/-1g, send its digit, and wait for capture=-1 before changing orientation:

| Serial digit | Axis reading | Capture |
|---|---|---|
| 0 | X approximately+1g | +X |
| 1 | X approximately-1g | -X |
| 2 | Y approximately+1g | +Y |
| 3 | Y approximately-1g | -Y |
| 4 | Z approximately+1g | +Z |
| 5 | Z approximately-1g | -Z |

Each face needs200 accepted samples. All six captures must pass the bias/scale/noise checks before accel=1. Captured face flags alone do not prove a valid fit. The sensor-to-aircraft axis transform is currently identity and must be checked against the actual mounting.

4. Send S to request saving; saves run on the slow task with NVS readback and a5s retry interval. Look for calibration_nvs=saved_readback. Send R only when deliberately discarding the current calibration and recapturing all faces. Serial C prints the command help; the periodic FC lines report status.
5. Look for gyro=1, accel=1 and baro=1 in the FC status. Pilot freshness also requires an actual Xbox connection. Other fault/disarm conditions still apply. Motors always remain disabled in this build.

The initial barometer reference is defined at power-on; if you move the board vertically during capture, reboot it stationary at the desired reference height. Keep the barometer away from direct airflow.
